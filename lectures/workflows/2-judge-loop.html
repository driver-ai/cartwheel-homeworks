LLM judges, generalized

The Judge Loop

How a human-labeled failure mode becomes a validated LLM judge. Three phases: prepare a judge-safe split into a training set, a development set, and a held-out test set; iterate against the development set, inspecting every disagreement before editing the prompt; then freeze the prompt and score it exactly once against the test set, data it has never seen.

Before you start

  • One evaluator, one failure mode. Everything below runs for a single mode. A product under evaluation usually has several; repeat the whole loop per mode, each with its own split, its own prompt, and its own frozen version — don't fold several modes into one judge.
  • An LLM judge is one kind of evaluator, not the default. Use it for modes that need interpretation — tone, relevance, whether a reply actually addresses what was asked. When a mode can be checked mechanically (a schema violation, a banned phrase, a broken link, a missing required field), a deterministic, code-based evaluator is simpler, cheaper, and exactly reproducible; save this loop for what code genuinely can't check.

What each set is actually for

  • The training set is the only one the prompt ever contains. A handful of its labeled traces get copied, verbatim, into the prompt text as worked examples (Figure 1, step 1.D) — the judge reads them every time it runs, the way a textbook's worked example stays on the page.
  • The development set never appears in the prompt. You run the finished prompt against it from the outside and compare its verdicts to the human labels; that outside comparison, not anything written into the prompt, is where it does its work. It's what Figure 2 iterates against, over and over.
  • The test set is handled exactly like the development set — run from the outside, never pasted into the prompt — but scored exactly once, after the prompt is frozen (Figure 3), so the result is an honest read instead of one more round of fitting.

Sizing this in practice

  • Labels: at least 30 present / 30 absent from independent conversations; closer to 100 total gives tighter confidence intervals.
  • Split: 20% training set / 40% development set / 40% test set, stratified, with a minimum-per-class guard on the development and test sets.
  • Revisions: at most two, counted from the first draft. Explain why you stopped revising.
  • Model: pin one judge model for the whole process; the development and test sets must use the same one.
  • Metric: TPR and TNR with a 95% Wilson interval each, never raw agreement — agreement hides a judge that always guesses the majority class.
  • Resuming: if a batch run is interrupted, rerun with the same judge ID — completed predictions are cached, so you only pay for what's missing. A revised prompt is registered as a new judge ID and evaluated fresh.

Reading the disagreement matrix

Judge: presentagreefalse alarm
Judge: absentmissagree
  • Rate on absent (the handout's TPR, since Pass/absent is defined as the positive class): of the traces where the failure is genuinely absent, what fraction did the judge also call absent? agree ÷ (agree + false alarm) down the absent column.
  • Rate on present (the handout's TNR): of the traces where the failure is genuinely present, what fraction did the judge also call present? agree ÷ (agree + miss) down the present column.
  • Both numbers, always. A judge that always says "absent" scores perfectly on one rate and zero on the other while posting high overall agreement whenever failures are rare — which is exactly the case overall agreement hides.
  • Report each rate with a 95% Wilson interval, not just the point estimate; when the dev and test sets only hold a few dozen traces each, that interval is often wider than the gap between two prompt versions.

Phase 3 of 3

Dev-set numbers vs. test-set numbers

  • Dev-set numbers are optimistic by construction — you looked at its disagreements to revise the prompt, so some of the improvement reflects fitting the examples you inspected.
  • The test set is the unbiased read. Report it once, after freezing, instead of treating dev-set alignment as the final result.
