Defining and maintaining evals, generalized

The Suite Loop

How a frozen taxonomy of failure modes becomes a versioned suite of Harbor tasks, and how that suite keeps working once the agent is live. First decide what earns a Harbor task — a failure mode that survives a quick fix, or a behavior worth protecting outright. Then write and classify each candidate's tasks, and run them as a gate on every change. After that, two separate things run on their own schedules, neither one triggered by the other: watching production continuously for a more honest read on failure modes you already know about, and recalibrating the judges that make that reading trustworthy.

Before you start

  • This loop assumes two things already exist. A frozen taxonomy of named failure modes, each with a binary present/absent definition and prevalence data from a labeled sample — see the Taxonomy Loop. And, for a subset of those modes, an already-frozen judge, measured for TPR and TNR against human labels — see the Judge Loop. Everything else — which modes are worth evaluating, which currently-reliable behaviors are worth protecting, code or judge or both — gets decided here, not before.
  • This loop uses Harbor's vocabulary throughout. A Harbor task is one versioned, reproducible trial: a request, a starting state, and the checks that grade the result. The shape transfers to any runner that can seed state, send a request, and score what comes back — but say "Harbor task," not just "task," so it's never confused with the request that feeds it or the failure mode it's testing.
  • Phases 3, 4, and 5 are not sequential steps of one pipeline. The gate (3) fires on every code change. Watching production (4) runs continuously, on its own clock. Recalibrating judges (5) runs periodically, on a completely different clock. All three can be happening at the same time.

Sizing this in practice

  • Timebox the quick fix: give a confirmed failure's prompt tweak, tool fix, or product change about one to two hours before it's allowed to earn a Harbor task at all.
  • Suite size: no fixed target — stop once every candidate you've decided is worth continually testing has at least one Harbor task. In practice that's often a dozen or so candidates; the task count is what falls out of that, not something to hit on its own.
  • Requests per candidate: a judgment call, not a rule. Weight it by prevalence or business impact — a candidate that matters a lot might get close to 5 requests so it isn't judged on one phrasing; a marginal one might get by with one or two.
  • Trials per Harbor task in the gate: 5, fixed. That's enough to tell a reliable behavior (5 of 5) from an unreliable one (3 of 5) without paying for more agent runs than the signal needs.
  • Deeper look at one capability: 10–20 trials outside the gate, on the one Harbor task you need a tighter number for. Watch for where the rate stops moving — that plateau is the real answer, not trial 20 itself.
  • Production sample (Phase 4): 1–5% of live traffic, continuously, graded by the judges only — code checks don't need this, since the gate already re-verifies them on every change.
  • Recalibration cadence (Phase 5): every few weeks, independent of the continuous sample above — its own fresh, hand-labeled batch, used only to recompute TPR/TNR.

Reading pass@k vs. passˆk

Three inputs, always: n is how many trials you observed, c is how many passed, and k is how many attempts you're asking about — not something the data gives you, a question you choose to ask of it (e.g. "if the product only gets 3 silent retries, what's the real success rate?").

pass@k = 1 − C(n−c, k) / C(n, k)
passˆk = C(c, k) / C(n, k)
where C(x, y) is "x choose y."

  • pass@k is the chance at least one of k attempts succeeds. It rises as k grows. Use it for a capability: can the agent do this at all, given a few tries.
  • passˆk is the chance all k attempts succeed. It falls as k grows. Use it for reliability: must this hold on every single interaction — a permission boundary, a confirmation step — not just most of them.
  • The gate never needs the general formula. At k=1, pass@1 reduces to exactly c/n — no combinatorics — which is the "baseline = c/5" in 2.D, and what 3.B compares a fresh run against. At k=n with c=n, passˆn = 1 — a regression's "blocks on any of the 5 failing" rule is that one special case. Both get computed exactly twice: once in 2.D to set them, again in every 3.A/3.B cycle to check a fresh run against them.

Going deeper on one capability (optional, outside the gate): run its Harbor task 10–20 times instead of 5, then compute pass@k for several different k from that same set of runs — 1, 3, 5, 10, 15. If it climbs fast and plateaus near 1 at a small k, that means retries would actually rescue the outcome: build that retry or fallback path into the product rather than spending more effort on the prompt. If it plateaus early and low, no number of retries will save it — that's a real capability gap needing real work. Either way, if this capability is anywhere near reliability-sensitive, compute passˆk at that same k before reporting results to anyone; it will look much worse than pass@k for the same data, and that's the honest number for "must hold every time."

pass@k never decreases as k grows, and typically plateaus somewhere in that 10–20 range — that plateau's height is what tells you which of the two situations above you're in.

Three things this isn't

  • Not a push for a fully green suite. A 100% pass rate across the whole suite usually means you've stopped finding problems, not that there aren't any. It's fine — expected, even — for one cheap regression check to sit at 100% forever; what should make you uneasy is the aggregate, when nothing left in the suite is still failing.
  • Not a reason to eval everything you observe. Most failure modes should die inside the timebox in Figure 1, to a prompt tweak or a product change, before they ever reach a Harbor task. Each trial is a full agent run, and a judge check adds a model call on top — a suite built to cover every observed behavior stops being one you can afford to run.
  • Not one pipeline. Figure 3 only protects against failure modes you already know about, and only on their five scripted requests. Figure 4 gives those same known modes a more honest reading against real traffic — it can't surface one that was never in the taxonomy; that takes a human reading traces with no checklist. Figure 5 keeps the judges doing that reading honest. All three are separate activities on separate schedules — not sequential stages of a single process.
