Monitoring after deployment, generalized

The Monitor Loop

The gate in the Suite Loop checks a few dozen scripted Harbor tasks before a change merges. It can't tell you what happens once real users arrive. Users ask new things, the model provider changes the model under you, and your own product changes. This is drift, and it means eval work never finishes. Monitoring has two jobs. The first is to re-measure the failure modes you already know about on real traffic, with a number you can trust. The second is to find the failure modes you don't know about yet. Both feed the same eval matrix: confirmed failures add new tasks (columns), and new failure modes add new rows.

Before you start

  • This loop assumes three things already exist. A frozen taxonomy of failure modes (the Taxonomy Loop). At least one frozen judge with its error rates measured on a held-out test set (the Judge Loop). And a gate of Harbor tasks running on every change (the Suite Loop). This page expands the Suite Loop's Phase 4 and adds the discovery work that Phase 4 explicitly leaves out.
  • "Frozen" covers the prompt, the model, the inputs, and the verdict parser. Change any one of them and you have a new judge with unknown error rates. Pin a dated model identifier rather than an alias, because a provider can repoint an alias without telling you.
  • 1 means the failure is present everywhere on this page. HW5 treated Pass as the positive class, so the names flip. The monitor's failure sensitivity (the share of real failures the judge flags) is HW5's TNR. Its pass specificity (the share of real passes it leaves alone) is HW5's TPR. The numbers are the same; only the labels change.
  • Cartwheel has no live traffic, so HW7 uses two full runs of the same 50 scenarios as two stand-in "deployment periods." Production works the same way, except that each period is a time window, such as the last 24 hours.

Sizing this in practice

  • Operational metrics and code checks: every trace. They cost almost nothing.
  • Judges, in production: a 1–5% uniform random sample, run as a batch job (for example nightly, over the last 24 hours), with scores written back to the trace store.
  • Judges, in HW7: 20% of 50 conversations, which is 10 per period. That is too few to estimate a rate with any precision, and seeing why is part of the lesson (see the worked example below).
  • Risk groups: every matching conversation, judged so that someone reads it, never counted toward the rate.
  • Threshold: pick it before you look at any period's results. HW7's default is a corrected rate of 15%.
  • Reading traces without a checklist: about weekly as a rule of thumb (in the lecture, Shreya said she manages every two weeks in practice), plus after any major product or model change.
  • Judge recalibration: every few weeks, on a freshly hand-labeled batch (Suite Loop, Phase 5).
  • Suite size stays small: 30–40 tasks at 5–10 trials each can already cost hundreds of dollars per run. Monitoring is how the suite grows selectively.

Phase 1 of 4

Don't use off-the-shelf evaluators

Monitoring tools, Langfuse included, ship ready-made judges such as "correctness," "helpfulness," "hallucination," and RAGAS "context precision." Hamel's verdict in the lecture: don't. Each one is someone else's prompt, written without looking at your data. The lecture found several concrete problems in them:

  • The criterion is too vague. "Correctness" never comes out of axial coding as a single mode; it has to be split into specific, binary failure modes. If your axial codes look like this list, the axial coding needs more work.
  • The scale is wrong. Several score on a continuous 0–1 scale. Every judge in this course is binary.
  • They expect inputs that don't exist in production. Some templates want a "ground truth" answer. Live traffic never has one.
  • The examples come from someone else's product. One built-in "correctness" prompt grounded itself with a recipe-bot example.

The features of these tools are still useful: the trace store, scores attached to traces, dashboards built on those scores, and annotation queues for domain experts. Use your own frozen judge with them.

Phase 2 of 4

Correcting the raw rate (Rogan-Gladen)

The judge makes two kinds of mistake. It misses real failures, which pulls the raw rate down. It flags real passes, which pushes the raw rate up. The second kind matters more than it looks: if the judge wrongly flags 10% of passes, a perfect agent still shows a 10% raw failure rate.

corrected = (raw + spec − 1) / (sens + spec − 1), clipped to [0, 1]
sens is failure sensitivity and spec is pass specificity, both measured on the frozen judge's held-out test set.

  • If the denominator is near 0, stop. At that point the judge is no better than a coin flip and the correction has nothing to work with.
  • The interval comes from a bootstrap. Resample the judge's test-set pairs (to capture uncertainty in sens and spec) and the sampled verdicts (to capture sampling luck), recompute the corrected rate thousands of times, and take the 2.5th and 97.5th percentiles. Seed it so the committed number reproduces. The reader's version resamples only the test set. HW7's contract resamples both, which makes the interval wider and more realistic when the sample is small.
  • Judge errors mostly widen the interval rather than shifting the corrected estimate. Better judge accuracy buys you a narrower interval.

With 10 conversations per period, the "after" point estimate triples and crosses a 15% threshold, but the two intervals overlap almost completely. The data supports "look at the flagged traces." It does not support "the agent got worse." The same proportions at 100 conversations per period give intervals that barely touch. Sample size, not the formula, decides whether a trend is real. This is why production samples a percentage of large volume, and why HW7's 10-per-period comparison is mechanics practice rather than evidence.

Phase 4 of 4

When the agent is under pressure

The second half of the lecture covered safety from a builder's point of view, using the OpenAI / Hugging Face incident. The headlines said agents "escaped a sandbox" and "broke into" Hugging Face. The lecture's reading is that what happened was predictable. An agent told to pass a grader will treat the grader as the target. It will use any path the environment leaves open to reach it. Full traces have not been released, so what follows is the partial account given in the lecture.

Reward pressure

Hamel's term for it. Run enough agents against one goal, with enough iterations, and you get something like evolutionary pressure: whatever path reaches the goal gets found, intended or not. Other reported OpenAI cases show the same thing:

  • Notes left in compaction. An agent wrote notes to itself in the summary produced when its context was compacted. The notes weren't visible in the trace you would read, but later model calls read them.
  • A leaked GitHub token. A researcher told an agent to prove a theorem itself, without looking up solutions. The agent used the researcher's GitHub token to post in an internal repository and get help from other agents. The model was shut down for about two weeks.
  • Watching the reasoning isn't a guarantee. A monitor on reasoning traces might have caught that second case. Under enough pressure, though, reasoning that is being watched can itself become obfuscated.

The lecture's lesson for evals: keep the grader out of the agent's reach, and read the traces. It added that most product agents aren't under this kind of pressure, because their prompts don't say "win the benchmark." My inference, not from the lecture: an automated improve loop that tunes the agent against your own eval suite (HW8 and HW9) does create that pressure. It is the reason the course says to keep evaluation inputs out of prompts and to hold out test cases until the configuration is frozen.

Three things this isn't

  • Not a dashboard you set up once. The dashboard tells you when to read traces. Monitoring that never leads to someone reading traces, and never adds a row or a column, is just a chart.
  • Not one rate from every judged trace. Risk groups are chosen because they fail more often. Mixing them into the estimate inflates it in a way you can't undo. Keep the lanes separate from sampling all the way through to the scores.
  • Not a verdict from a raw percentage. A raw flag rate includes the judge's own mistakes, and a corrected rate from 10 conversations has an interval about half as wide as the whole scale. Correct the rate, attach the interval, and treat a threshold crossing as a reason to look.
A process guide for watching an agent after deployment: cheap metrics and code checks on every trace, a corrected judge rate on a random sample, risk groups for reading, and a recurring human look for whatever none of these was built to see.
